# Cloud Courier · local review slice

An original portrait delivery game for Alexander Banderov. Carry porcelain, an oversized kite, or pastries through floating neighborhoods. Wide mint bridges provide a sheltered detour; coral bridges save distance but expose the parcel to wind. Steadying slows movement and reduces wind drift and turn strain. Falling triggers a checkpoint rescue and damages the parcel. Reach the golden postbox before the deadline with the parcel intact.

## Play locally

Double-click `play.cmd`, then open **http://127.0.0.1:8791/** in Edge or Chrome. Node must be installed. Close the server window or press Ctrl+C when finished. It serves the already staged `dist/portfolio` build; no installation, Worker, account or remote game assets are required. A port conflict can be avoided with `$env:COURIER_PORT='8792'; node server.cjs` in this directory. Do not open index.html directly through file:// because browser module policies differ.

- Touch or mouse: drag the lower-left pad. Dispatch offers hold or tap-to-toggle STEADY; keyboard Space follows the same setting. The choice persists. Pause, blur, resize and new runs release steadying, including toggles. The button text and pressed state show the current action.
- Keyboard: WASD or arrows, Space to steady, P or Escape to pause. The pause button works with all inputs.
- Pause, losing and winning offer same-seed retry and dispatch desk. Window blur, hiding or resize pauses the run and clears held inputs; resume is explicit.
- Route seed is editable at dispatch and visible during play. A bug report should include seed, contract, district, generator version (g1), viewport, browser and controls. `?debug` exposes a deterministic stepping/position harness, absent from normal play.

## Why return

**Balance review finding:** gold is verified through full input-driven runs. Matched steering tests below show a speed/condition frontier, but route results depend strongly on centering cadence and steadying. Safe gold routes remain available. The loop remains a review prototype; human steering, shortcut reward and gold differentiation need owner feedback before expansion.

Three parcels change speed, wind response, fragility and deadline. Every seeded neighborhood has six independent forks; a gold medal requires both at least 85% parcel condition and the contract's time target. Players can learn a route, mix safe bridges and shortcuts, and improve their medal. Saved medals retain the best seal for each seed/contract/district; the latest 120 routes are retained. Delivery streaks last for the current session; best streak and delivery count persist. Three deliveries unlock Copper Heights (stronger wind and a copper palette) and two coat colors. This is a small mastery loop, without an energy timer, grind currency, forced ads or daily punishment. Daily routes use a UTC date seed and the same tea/garden contract for everyone, with no streak penalty for missing a day.

These mechanics are implemented; enjoyment and return rate have not been established by independent human playtests. Moving platforms, physical parcel swinging, ghosts, leaderboards and longer progression are intentionally deferred until the core route choice receives owner feedback.

## Decision and provenance

Canvas 2D was selected after a narrow comparison: a top-down portrait view shows bridge width, direction and parcel state without camera occlusion; HTML controls remain crisp and accessible. Canvas is a mature browser drawing API ([MDN reference](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API)). Godot could support the game and matches the owner's experience, but would add an export/runtime footprint that is unnecessary for this small loop. Small Three.js 3D could add depth, but would need more camera, touch and occlusion work before proving the same route decision. No engine/dependency replacement was made elsewhere.

All shapes, courier silhouette, cloud clusters, roofs, postboxes, bridge boards, palette and animation are deliberately authored Canvas/CSS geometry in `src/app.mjs` and `src/style.css`. No bitmap art, sprite pack, font download, generated music, synthetic voice, video, image-model output or internal generated reference was used. No supplied character drawings or book/Ovi canon were incorporated. Root handoff and reference/archive inventory were inspected read-only for constraints and project boundaries; existing games are not source material for this game's cast. System fonts come from the device. The prototype is intentionally silent; it creates no AudioContext and has no playback to resume after an interruption. Audio behavior/audible quality are untested and adding owner-authored sound requires explicit gesture resume, SDK mute priority and ad/background suspension.

From this directory:

```powershell

```

Build syntax-checks every runtime module, copies a fixed allowlist into `dist/portal` and `dist/portfolio`, measures **all files actually present** in each release recursively (including any unexpected stale files), and fails at 20,000,000 bytes or above. It also fails above the 15,000,000-byte target. `size-portal.json` and `size-portfolio.json` give exact file counts, bytes and SHA-256 values. **Verified release: 6 runtime files, 42,477 bytes total uncompressed (0.042477 MB)** in each target. The ZIP has index.html at its root. ZIP size is not the budget measurement. No essential game asset is moved to an external URL; the only optional external script is the required CrazyGames platform SDK. No source/tests/screenshots/docs are in the runtime package.

## CrazyGames adapter

`src/platform.mjs` loads SDK v3 only on a CrazyGames hostname (or `?platform=crazygames` for explicit SDK testing). It awaits initialization, checks environment, reports loading and actual gameplay start/stop, and calls happytime for a delivery. Menus, pause, result, background and page exit stop gameplay. The adapter uses the Data module exclusively when active on CrazyGames, including guests; standalone uses namespaced localStorage. Corrupt/version-mismatched saves are sanitized/reset. Disabled SDK environments fall back to standalone outside CrazyGames. On portal SDK failure, play continues with clearly labeled session-only progress, without reading or writing a competing local save. Script load and init each have a six-second timeout; failed saves retain current session progress.

No ad is requested or displayed. The isolated ad-callback hook pauses the game for a later reviewed Full Launch implementation and leaves resumption to a user action. No mechanic depends on watching an ad. The silent prototype records SDK mute state for future owner audio.

Current official documentation checked 2026-10-07: [SDK initialization/environments](https://docs.crazygames.com/sdk/intro/), [game lifecycle/settings](https://docs.crazygames.com/sdk/game/), [Data module](https://docs.crazygames.com/sdk/data/), [technical requirements](https://docs.crazygames.com/requirements/technical/). Current platform limits distinguish total size from initial download/mobile eligibility; **the owner's stricter total uncompressed under-20,000,000-byte limit governs this project**. Basic Launch prohibits ads. Select Progress Save in submission if using Data. The bundle is staged for review; portal initialization, cloud save and acceptance remain unverified in the actual QA environment. No private preview URL was fetched and nothing was submitted.

## Verification scope

`test/logic.mjs` checks 3,272,400 centerline samples across 1,800 deterministic routes, then drives 60 complete sheltered-route deliveries through actual physics with no rescues and full condition. It also covers deadline loss, parcel break/rescue, medals, save restoration and daily date. This establishes a reachable safe alternative, not a guarantee every player can handle every shortcut.

### Actual shortcut and mixed-route balance sweep

`node test/balance.mjs` passed with exit 0: **1,716 input-driven simulations** over 22 seeds (first-flight, the 2026-10-07 daily seed, balance-0 through balance-19), all three contracts and both districts. The final report is `balance-results.json`; per-run status/time/condition/rescues/score/medal and min/median/max distributions are included. `balance-console.txt` records the output. The initial endpoint-only report is preserved as `balance-baseline-endpoint.json` (792 runs, initial evaluation exit 1).

Each run starts through `newRun` and advances only through the production `step` at 120 Hz. The harness never changes position, time, condition, status, wind or medals. It samples analog steering at 10 Hz, holds controls between samples and adds ±3.4-degree aiming wobble. Endpoint policies aim at visible bridge endpoints without lateral wind cancellation. Reactive policies aim along a local 60-unit bridge lookahead; the corrected-shortcut policy uses a 20-unit lookahead, steadies when lateral error exceeds 2.5 units, within 65 units of an endpoint, and for 0.6 seconds after turning. It uses current position/visible geometry, with no future wind prediction. These are robot steering policies, not human results; at a 320px screen, a 2.5-world-unit correction is about 1.9 screen pixels and may demand more precision than a player can maintain.

Median actual times below come from 22 seeds per row. Every listed 10 Hz policy completed all 22 runs with gold; fast sheltered condition varies, while corrected-shortcut and mixed-reactive condition is 100% with zero rescues.

Across districts, corrected shortcuts beat fast sheltered **score** on only 15/44 tea runs, 0/44 kite runs and 22/44 express runs (one express tie). Thus condition-versus-time is a real measured tradeoff, but gold is readily available through sheltered routes and kite shortcuts have insufficient score incentive. Steady-all shortcut runs save distance/time versus steady-all sheltered runs for tea/express. Kite's endpoint-only shortcut policy earned 10/22 golds in Gardens and lost all 22 runs in Heights. Unbraced endpoint-only or 60-unit-lookahead shortcut policies lost every run for all contracts/districts. These negative results are retained rather than hidden by the passing attainable-gold assertions.

Corrected shortcuts completed 117/132 with only 40 golds, including **zero kite golds** and 12/22 kite Heights losses. Mixed reactive earned all tea golds and all express Gardens golds, but was also fragile for kite and express Heights. This is evidence of tight control tolerance, not physical-device proof.

The first evaluation assumed every steady shortcut would yield gold; that unsupported assertion failed. The final assertions check actual gold attainment by input-driven completion for every sampled seed/contract/district, preserve zero-rescue cautious sheltered reachability, and verify the precise corrected shortcut policy's measured gold outcome. No production threshold or physics was changed to make the report pass.

**Recommended next balance trial:** preserve the current release as baseline, then separately compare more forgiving kite wind/bridge tolerance and stronger safe-turn strain or a route-specific mastery target. Tightening only the gold timer would encourage a currently unrewarding route and could punish cautious mobile players. Start with human portrait steering and route-choice feedback before selecting a change; no new mechanic or automatic rebalance was implemented in this sweep. Successful robot controls establish attainability, not fun, readability at speed or a proven retention loop.

### Matched controls and the speed/condition frontier

This follow-up refines the preceding exploratory comparison: **do not generalize its endpoint/60-unit-lookahead failures to all shortcut steering**. `node test/matched-balance.mjs` passed, running 1,584 additional matched trials (3,300 simulations including its imported 1,716-run baseline). `matched-balance-results.json` records 264 **per-route, per-cadence** frontiers with successful measured policy points (time rounded to 0.01s); `matched-balance-console.txt` records both sweeps. `balance-console-before-matched.txt` preserves the earlier console before rescue observation was confined to the input cadence. All runtime and gold thresholds remain unchanged.

Safe and shortcut policies now use the **same** 20-unit lookahead, 12-unit waypoint arrival test, aiming wobble, sample schedule and steering formula. Only route selection and steady mode vary: never, always, or the same edge/endpoint/after-turn rule. Ten-Hz controls update every 100ms with ±3.4-degree wobble; five-Hz controls update every 200ms with ±8.6-degree wobble. Output is held between updates while physics integrates at 120Hz. No controller decision or rescue reaction occurs at 120Hz. Every run records update count and the fraction of time spent steadying; assertions check update frequency and always/never duty cycles.

The controller receives **exact sampled world x/y, elapsed time, rescue/checkpoint cue, preselected bridge geometry and its safe/windy color classification**. It does not receive velocity, condition, instantaneous wind, phase or forecasts and does not search for optimal future controls. Endpoints for the preselected route are known, including portions outside the current viewport; this is a limitation, even though steering uses only a 20-unit local lookahead. Exact world coordinates and geometry are ideal observations, not estimates extracted from screenshots. The direction and ±3.4/8.6-degree wobble are continuous analog inputs, not measured thumb noise. This is bounded-cadence geometry feedback, **not an optimal 120Hz controller and not evidence of human practical precision**. Perceptual delay, imprecise bridge-center estimation, visual clutter and hand fatigue have not been modeled. A 2.5-unit centering threshold is roughly 1.9 pixels at 320px width.

At **5 Hz**, the matched safe/unsteady policy completed **132/132 runs with gold**. The matched shortcut/always-steady policy also completed **132/132 with gold and 100% condition**. Matched shortcut/unsteady completed only 14/132 and earned zero golds; kite lost every unsteady shortcut run at both cadences. Therefore steadying plus local centering is a supported input policy in these ideal-observation simulations, and the earlier kite endpoint policy's failure does not establish that all cautious kite shortcuts fail.

The frontier includes a run when no successful measured alternative for the **same seed, contract, district and cadence** is both no slower and in no worse condition, with one strict improvement. It uses centisecond time and full-precision condition; tiny differences can affect membership and are not necessarily perceptible to players. Failures are excluded from completion medians/frontiers and remain in run/win/loss counts. Median rows above illustrate the tradeoff; they are not themselves a computed global frontier.

At 5 Hz, safe/unsteady belongs to the frontier for **44/44 routes in each contract**. Shortcut/always-steady belongs for **27/44 tea, 39/44 kite and 42/44 express** routes: extra time can buy an intact parcel, while safe routing preserves a fast and forgiving alternative. Some conditional-steady policies dominate always-steady on individual routes. At 10 Hz with less wobble, unsteady tea/express shortcuts belong to every route's frontier and their Gardens medians are 21.01s/100% and 18.85s/100%, versus safe/unsteady 25.27s/98.19% and 22.98s/97.25%. These precise shortcut results deteriorate sharply under the slower/noisier schedule, which is the actual measured mastery/risk signal. Changing cadence and wobble together means the experiment does **not** isolate the causal effect of either one alone.

This establishes a measured frontier under stated controllers, not a human shortcut reward or fun claim. Gold remains fairly coarse: both cautious and fast sheltered policies can earn it. Preserve favorable safe routes; **do not add arbitrary safe-path punishment based on these robot results**. The earlier suggestions of stronger safe-turn strain are provisional experiments, not selected changes. Before any rebalance, the owner should compare safe and fully steadied shortcut runs on a real portrait phone, assess whether the difference is enjoyable and readable, and decide whether score incentives or medal distinctions need a focused trial. No new mechanic has been added.
